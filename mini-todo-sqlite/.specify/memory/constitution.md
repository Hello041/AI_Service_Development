# Mini Todo SQLite 헌장

## 핵심 원칙

### I. Next.js App Router 아키텍처
프로젝트는 반드시 Next.js의 App Router(`app/` 디렉터리 규칙)를 사용하여 구축해야
하며, 레거시 Pages Router는 사용하지 않는다. 모든 라우팅, 레이아웃, 라우트
핸들러는 App Router 규칙(`page.tsx`, `layout.tsx`, `route.ts`, 기본은 서버
컴포넌트, 상호작용이 필요한 경우에만 클라이언트 컴포넌트)을 따라야 한다.
모든 소스 코드는 반드시 TypeScript(`.ts`/`.tsx`)로 작성해야 하며, 순수
JavaScript 소스 파일은 허용되지 않는다.

근거: App Router는 Next.js가 앞으로 계속 지원할 라우팅 모델이다. 이를
Pages Router나 타입이 없는 JavaScript 코드와 섞어 쓰면 코드베이스가
일관성을 잃고, 이 프로젝트가 의존하는 타입 안전성 보장이 무너진다.

### II. 엄격한 타입 안전성 (NON-NEGOTIABLE)
`any` 타입은 암묵적(implicit) `any`를 포함하여 코드베이스 어디에서도
사용해서는 안 된다(TypeScript의 `strict` 및 `noImplicitAny` 컴파일러
옵션은 항상 활성화 상태를 유지해야 한다). 값의 형태를 정말로 알 수 없는
경우에는 `any` 대신 `unknown`과 명시적인 타입 좁히기(타입 가드, `zod` 방식
검증 등)를 함께 사용해야 한다. 타입 정의가 없는 서드파티 모듈은 `any`로
캐스팅하지 말고 로컬 타입 선언을 작성해 주어야 한다.

근거: `any`는 타입 검사기를 조용히 무력화시켜 TypeScript를 쓰는 목적을
무너뜨리고, 런타임 타입 오류가 사용자에게 그대로 노출될 위험을 만든다.

### III. 일관된 JSON API 응답
모든 API 라우트(`app/api/**/route.ts` 이하)는 반드시 `Content-Type:
application/json`으로 응답해야 하며, 성공/실패 케이스 모두에 대해 일관된
응답 포맷(envelope)을 사용해야 한다. 성공 응답과 에러 응답은 모든
엔드포인트에서 동일한 하나의 형태(예: 한 곳에서 정의하고 재사용하는 공통
`{ data }` / `{ error }` envelope)를 사용해야 하며, 임시방편의 일반 텍스트,
HTML, 엔드포인트별 개별 포맷을 사용해서는 안 된다. 에러는 적절한 HTTP
상태 코드와 함께 JSON으로 노출되어야 하며, JSON이 아닌 출력을 만드는
처리되지 않은 예외로 던져져서는 안 된다.

근거: 통일된 JSON 계약을 사용하면 어떤 클라이언트든(앱 자체의 프론트엔드,
테스트, 외부 소비자) 엔드포인트별 예외 처리 없이 모든 API 응답을 동일한
방식으로 파싱할 수 있다.

## 기술 스택

- 프레임워크: Next.js, App Router만 사용.
- 언어: 전체 코드베이스(앱 코드, API 라우트, 지원되는 범위의 설정 파일)에
  TypeScript를 사용하며, 원칙 II에 따라 `any`는 금지된다.
- API 계층: 요청/응답 본문은 JSON만 사용하며, 원칙 III에 따른 단일 공유
  응답 envelope 형태를 사용한다.

## 개발 워크플로

- 코드 리뷰(혼자 작업할 때는 셀프 리뷰)에서는 병합 전에 다음을 반드시
  확인해야 한다: Pages Router 관련 산출물이 추가되지 않았는지, 명시적이든
  암묵적이든 `any`가 추가되지 않았는지, 신규/수정된 API 라우트가 성공과
  실패 경로 모두에서 공유 JSON envelope를 반환하는지.
- 변경 사항이 완료되었다고 간주되기 전에 반드시 `npm run lint`를
  통과해야 한다(ESLint 설정이 이미 TypeScript 규칙을 강제하고 있음).

## 거버넌스

이 헌장은 이 저장소 내의 상충되는 임시 관행보다 우선한다. 개정은 이
파일을 직접 수정하고, 상단의 동기화 영향 보고서를 갱신하며, 시맨틱
버저닝 규칙에 따라 버전을 올리는 방식으로 이루어진다: 원칙의 하위
호환되지 않는 제거나 재정의는 MAJOR, 새로운 원칙 추가나 실질적인
가이드 확장은 MINOR, 설명 보완이나 문구 수정은 PATCH로 처리한다. 모든
개정은 반드시 `LAST_AMENDED_DATE`를 갱신해야 한다. 이 헌장 준수 여부는
위 개발 워크플로에서 설명한 대로 코드 리뷰 시 확인되어야 하며, 예외가
필요한 경우 해당 PR/변경 설명에 명시적이고 문서화된 근거를 남겨야 한다.
